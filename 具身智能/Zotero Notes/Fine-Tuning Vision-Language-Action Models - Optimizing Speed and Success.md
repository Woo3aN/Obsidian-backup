## 基本情况

- **一句话**：输入「多路相机图像 + 机器人本体状态 + 语言指令」→ 输出「未来 K 步的连续关节/末端位姿动作」，一次前向出整块动作（action chunk）。
- **开源**：代码开源（openvla-oft）/ 权重开（LIBERO 与 ALOHA 的 checkpoint）/ 数据不开（LIBERO 用公开仿真数据，ALOHA 是自采的 20–300 条演示）。
- **和读过的哪篇最像、差在哪**：基座是 OpenVLA（自回归 + 离散动作 token）；对标 π0（flow matching + action expert）与 RDT-1B（扩散）。差别在于这篇不谈新架构，只谈「微调配方」——同样的 7B VLA，换掉解码方式/动作表示/损失函数，速度 26–43×、LIBERO 97.1%。
- **一句话定位**：这是一篇**工程配方论文**，不是模型论文。它的贡献是「证明原来那套默认做法是可以被推翻的」，并且给出推翻之后的具体数字。

## ① 动机

### 1.1 任务是什么（具体到一句指令）

一条 ALOHA 流水线任务：**左臂把绿碗挪到桌子中间，右臂用金属勺把指令指定的配料舀进碗里**。指令可能是 `scoop raisins into bowl`，也可能是 `scoop almonds and green M&Ms into bowl` 或 `scoop pretzels into bowl`。

同一套场景、同一套动作，只有目标物不同——这正是语言必须起作用的地方。

任务共同点：**双臂**、**25 Hz 控制频率**、**3 个相机**（1 顶视 + 2 腕部）。而 OpenVLA 预训练时见的是**单臂 + 单相机 + 3–10 Hz + 相对末端位姿动作**。分布差得非常远。

### 1.2 照搬原配方会卡在哪

最省事的做法是照抄预训练配方：自回归解码 + 7 个离散动作 token + 交叉熵。问题全在速度和可扩展性上：

| 环节 | 数字 |
|---|---|
| 生成单步动作（7 维） | 7 次串行前向 = **0.33 s**（A100） |
| 实际控制频率 | **3–5 Hz** |
| 双臂高频机器人需要 | **25–50+ Hz** |

想「多看几步」（action chunking，一次预测未来 K 步）本来能提分，但自回归下要 **K×D 次**串行前向（K=25、D=14 → 350 次）——越想办法提速越慢。

### 1.3 已有两条路线都不够

| 路线 | 代表 | 效果 | 局限 |
|---|---|---|---|
| 改 tokenization | MiniVLA、FAST | 2–13× | 仍是自回归，逐 token 生成的天花板还在；FAST 块间延迟 **750 ms** |
| 生成式（扩散 / flow matching） | π0、RDT-1B | 一次出整块 | 训练收敛慢、推理要多步去噪（π0 是 10 步） |

750 ms 是什么概念：25 Hz 下一个控制周期是 40 ms，停 750 ms 等于机器人每秒卡住四分之三秒。

### 1.4 作者的押注

> **微调配方比模型架构、比预训练数据覆盖更重要。**
> 把「怎么解码、怎么表示动作、用什么损失」这三件事选对，一个只在单臂数据上预训练过的 7B VLA，能打赢专门为双臂预训练的 π0（8K 小时双臂数据）和 RDT-1B（6K episodes）。

拆成三个层层递进的子结论：

1. **并行解码 + action chunking**：既提速又提分（+14 点）；
2. **连续动作表示**：比离散再 +5 点；
3. **L1 回归**：与扩散打平（95.3 vs 95.4），但训练收敛快、推理只要 1 步（扩散 50 步）。

### 2.0 原版 OpenVLA 的完整前向（逐步张量流）

先约定：`B` 是 batch，`H` 是 Llama 的隐藏维 **4096**，`D` 是动作维度（LIBERO 7 / ALOHA 14），`K` 是动作块长度。

| 步 | 动作 | 张量形状 |
|---|---|---|
| 1 | 读入一张 RGB 图，缩放到 224×224，复制成 6 通道（SigLIP 3 + DINOv2 3） | `(B, 6, 224, 224)` |
| 2 | 按通道切成两份，分别进 SigLIP 与 DINOv2 | 各 `(B, 3, 224, 224)` |
| 3 | 两个 ViT 各自把图切成 14×14 网格再展平 → 每个 patch 一个向量 | 各 `(B, 256, D_vit)` |
| 4 | **在隐藏维上拼接**（不是加，是 concat） | `(B, 256, D_sig+D_din)` |
| 5 | 3 层 MLP projector（GELU）投到语言空间 | `(B, 256, 4096)` |
| 6 | 指令 `put eggplant into pot` 过 tokenizer + embedding | `(B, ~20, 4096)` |
| 7 | 序列拼接：视觉 patch **插在 BOS 之后**，指令跟在后面 | `(B, ~277, 4096)` |
| 8 | Llama-2 7B 前向（32 层，因果注意力） | `(B, ~277, 4096)` |
| 9 | `lm_head` 投到词表 | `(B, ~277, 32000)` |
| 10 | 只取**最后 7 个位置**的 logits，各自 argmax | 7 个整数编号 |
| 11 | 编号 → 桶中心 → 反归一化 | `(7,)` 的动作 |

**第 10 步是整篇论文的起爆点**：为什么是「最后 7 个位置」？因为原版是**先把 7 个动作词追加到序列末尾，再一个接一个预测**。第一次前向后，只有第 1 个动作词有值；把它接回去再跑一次，才有第 2 个。所以真实流程是 7 次前向，每次都跑完整的 277 个 token。

**第 9 步的 32000 是 Llama-2 的词表大小**。动作词并不新增词表，而是**占用词表末尾的 256 个位置**——代码里 `ACTION_TOKEN_BEGIN_IDX = 31743`，也就是第 31743~31999 这 256 个词专用于动作分桶。这个设计很取巧：不需要改模型结构，直接在原词表里占坑。

前五处合起来叫 **OFT**（Optimized Fine-Tuning），第六处加上之后叫 **OFT+**。

| # | OpenVLA 原版 | OFT | 为什么 | 出处 |
|---|---|---|---|---|
| 1 | 1 张第三人称图 | 1–3 张（ALOHA 顶视+双腕），共享 SigLIP+DINOv2，每张 256 patch | 双臂任务必须看腕部近景 | §4.2 L116；`modeling_prismatic.py:196-225` |

六处**互相咬合**，不是六个独立小改进：没有 3，5 跑不动；没有 5，1 和 2 增加的计算量吃不下；没有 4，3 和 5 只能停在 90.2%。

### 改动 1：一张图 → 多张图

#### 原版怎么处理一张图

OpenVLA 的视觉部分有个特别设计，叫**融合骨干**（fused backbone）：同一张图**同时喂给两个不同的视觉编码器**。

| 编码器 | 擅长什么 | 在本篇的作用 |
|---|---|---|
| **SigLIP** | 语义、图文对齐（「这是不是青椒」） | 让语言和视觉能对上 |
| **DINOv2** | 空间、纹理、边缘（「边缘在这、距离多远」） | 提供精细的几何信息 |

两个编码器各出 256 个 patch 向量，然后**在隐藏维上拼接**成一个更长的向量。

> **容易搞混的一点**：拼接后 token 数**还是 256**，不是 512。变的是「每个 token 变胖了」，不是「token 变多了」。这跟后面「多相机」时 token 变多（256→768）是两件事。

代码里的痕迹很直白——送进模型的 `pixel_values` 是 **6 通道**：

```python
img, img_fused = torch.split(pixel_values, [3, 3], dim=1)   # 前3给SigLIP，后3给DINOv2
patches, patches_fused = self.featurizer(img), self.fused_featurizer(img_fused)
return torch.cat([patches, patches_fused], dim=2)            # 沿隐藏维拼
```

#### 问题

ALOHA 上有 **3 个相机**：顶视 1 个、左右手腕各 1 个。只用顶视会怎样？

叠 T 恤的时候，两条机械臂自己就把桌面挡了一半；而「布料现在卡在哪个指缝里」「夹爪离袖口还有几厘米」，这些只在**腕部相机**的画面里。顶视图看到的是「机械臂的后背」。

#### 改法

`num_images_in_input` 从 1 改成 3。每张图**依次走同一套**编码器和 projector（权重完全共享），各出 256 token，然后沿**序列维**拼起来：

```
顶视图   → 256 个 token ┐
左腕图   → 256 个 token ├→ 768 个 token 一起送进 Llama
右腕图   → 256 个 token ┘
```

代码就是循环切 6 通道：

```python
images = torch.split(pixel_values, [6] * self.num_images_in_input, dim=1)  # 每张图6通道
for img in images:
    img_regular, img_fused = torch.split(img, [3, 3], dim=1)
    all_patches.append(torch.cat([self.featurizer(img_regular),
                                  self.fused_featurizer(img_fused)], dim=2))
```

#### 为什么共享权重而不是三套编码器

数据量。ALOHA 每个任务只有 **20–300 条**示教。从零训三套视觉编码器（每套几亿参数）必然过拟合到死。共享权重等于把「怎么看图」这件事上的数据量乘了 3，而且三个视角用的是同一批相机、成像特性相同，没必要分开学。

另一个隐含好处：**视角之间的表示是同一套坐标系**。模型不需要额外学习「腕部图和顶视图的特征怎么对齐」，因为它们在同一个特征空间里。

#### 代价与收益

代价是**序列变长**：token 从 256 涨到 768，注意力计算按长度平方涨（768² vs 256²，约 9 倍）。

但因为有并行解码（改动 3），这点代价完全吃得下：LIBERO 上加了腕部图（1 张 → 2 张）后，吞吐从 109.7 Hz 掉到 **71.4 Hz**，仍远高于控制频率；而成功率从 95.3% 涨到 **97.1%**。

### 改动 2：本体状态（proprioception）

#### 是什么

**本体感觉**：你闭着眼也知道自己右手举在头顶还是垂在身侧，靠的不是眼睛，是肌肉和关节的感受器。

机器人的版本就是**关节角读数**。ALOHA 双臂，每条臂 6 个旋转关节 + 1 个夹爪 = 7 维，双臂 **14 维**。这 14 个数就是机器人此刻的「姿势」。

#### 原版为什么不需要，ALOHA 为什么必须

原版只看图。这在单臂、低频场景下勉强能用，原因有两个：动作是**相对**末端位姿的增量（「往前挪 2 厘米」），相对量不需要知道起点；相机和控制器频率接近，图像延迟不致命。

到 ALOHA 上这三条全变了：

1. **图像有遮挡和延迟**：相机 30 Hz、控制器 25 Hz，图总是「过去」的。关节角是即时的、精确的。
2. **动作空间变成绝对量**：ALOHA 的动作是**绝对关节角目标**（「左手腕转到 0.42 弧度」）。不给起点，模型等于在盲猜。
3. **左右臂容易搞混**：顶视图里两条臂长得一样，光看图分不清该动哪条。

#### 改法

```
14 个归一化后的数 → 2 层 MLP(GELU) → 4096 维 → 变成 1 个 token
```

然后**拼在 768 个视觉 token 的后面**。代码只有十行：

```python
proprio = proprio.reshape(bsz, -1)              # (B, 14)
proprio_features = proprio_projector(proprio)   # (B, 4096)
proprio_features = proprio_features.unsqueeze(1)# (B, 1, 4096)
return torch.cat((projected_patch_embeddings, proprio_features), dim=1)
```

#### 为什么压成 1 个 token，而不是 14 个

这是最容易问的问题。三个理由：

1. **这 14 个数没有空间结构**。图像切 256 块是因为「左上角」和「右下角」确实是不同的东西，需要各自的位置。关节角没有这种结构——它就是 14 个标量。
2. **它们之间没有「前后文」关系**。Transformer 的注意力机制是用来建模「第 5 个词和第 9 个词有关系」这类东西的。关节 3 和关节 4 只是两根相邻的连杆，不需要让它们互相注意。
3. **信息量小**。一个 4096 维向量塞 14 个归一化到 [-1,1] 的数，绰绰有余（相当于用 292 个浮点位存一个数）。

占 1 个位置，比占 14 个位置省序列长度——这在 768 个视觉 token 已经很挤的情况下很重要。

#### 归一化（细节，但影响很大）

14 个关节的量纲完全不同：有的转 ±180°，有的只动 ±0.05 米，夹爪是 0~1。直接喂进去，模型会被大数值的关节主导。

| 平台 | 归一化方式 | 含义 | 为什么这么选 |
|---|---|---|---|
| LIBERO | `BOUNDS_Q99` | 1%/99% 分位数当上下界，超出截断 | 仿真里偶有极端姿态，分位数更稳 |
| ALOHA | `BOUNDS` | 最小/最大值 | 遥操作数据本身干净，用满量程 |
| Bridge | `BOUNDS_Q99` | 同 LIBERO | 多机构采集，脏数据多 |

用分位数而不是最大最小值，是防止个别离谱的示教（关节转到底）把量程拉爆，导致正常动作全被压到 [-0.1, 0.1] 这种窄区间里。

#### 代码里的另一处

`prismatic/vla/constants.py` 里给每个平台写了常量，**按命令行参数自动选择**：

```python
LIBERO_CONSTANTS = {"NUM_ACTIONS_CHUNK": 8,  "ACTION_DIM": 7,  "PROPRIO_DIM": 8,  ...}
ALOHA_CONSTANTS  = {"NUM_ACTIONS_CHUNK": 25, "ACTION_DIM": 14, "PROPRIO_DIM": 14, ...}
BRIDGE_CONSTANTS = {"NUM_ACTIONS_CHUNK": 5,  "ACTION_DIM": 7,  "PROPRIO_DIM": 7,  ...}
```

也就是说：**这篇不做跨本体统一**。换机器人就是换一套常量 + 重新微调。这是它的工程性，也是它的局限（不做通用本体）。

### 改动 3：并行解码（提速核心）

#### 原版逐 token 生成，走一遍

```
第 1 次前向：[BOS] + 256图token + 20指令token                → 第1个词 "128"
第 2 次前向：[BOS] + ... + "128"                             → 第2个词 "132"
第 3 次前向：[BOS] + ... + "132"                             → 第3个词 "14"
...
第 7 次前向：[BOS] + ...                                     → 第7个词 "255"
```

卡住它的是**因果 mask**（causal mask）：一个上三角的遮罩矩阵，规定「第 i 个位置只能看到第 1 到第 i 个位置」。

```
       位置:  1  2  3  4 ...
位置 1        ✓  ✗  ✗  ✗        ✓ = 可以看
位置 2        ✓  ✓  ✗  ✗        ✗ = 被遮住
位置 3        ✓  ✓  ✓  ✗
位置 4        ✓  ✓  ✓  ✓
```

这是语言模型「不能偷看答案」的机制。也正因为如此，第 i 个词必须等第 i-1 个词生成完才能算。

#### 改成并行要动两处

**① 输入侧：不再喂「已生成的词」，改成喂一排空占位符。**

图 2 左半那些**黄色小方块**就是占位符。它们的内容完全相同（一个固定值的 embedding），**只有位置编码不同**——位置编码是告诉模型「你是第几号位置」的信号。

没有位置编码会怎样？一排一模一样的向量，模型根本分不清哪个对应「第 1 步」哪个对应「第 25 步」，输出就成了一团。

你可以理解为：答题卡上印好了 350 个空格（ALOHA：25×14），等着一起填。

**② mask 侧：因果遮罩 → 全 1 遮罩（双向注意力）。**

```
       位置:  1  2  3  4 ...
位置 1        ✓  ✓  ✓  ✓        全都可见
位置 2        ✓  ✓  ✓  ✓
位置 3        ✓  ✓  ✓  ✓
位置 4        ✓  ✓  ✓  ✓
```

图 2 右边那个框写着 **bidirectional attention**。现在每个动作位置都能看到：所有图像 token、所有指令 token、**以及所有其他动作位置**。

#### 为什么必须双向

因为动作之间本来就强相关。「第 5 步手腕往上抬 2cm」和「第 6 步继续往上 1cm」是一条连续轨迹上的两个点，让它们互相看得见，模型填格时才能保证**整段连贯**。

因果 mask 下第 5 步看不到第 6 步，等于让模型「猜」后面的轨迹——这在生成文本时是对的（文本本来就是顺着写的），但在生成一段**已经知道长度的轨迹**时是浪费。

#### 为什么这样不会变笨

理论上，自回归能表示任意序列分布，表达力更强。但这里有两个区别：

1. **输出是固定长度的**：不像文本有「该说几个词」的不确定性，动作块长度是 K×D 定死的。
2. **答案不在输入里**：训练时占位符是空的，模型必须从图像和指令里推断全部 350 个数，没有「抄近路」的机会。

实验也证实了：LIBERO 四个 suite 上没有一个退化。作者的原话是「while parallel decoding may theoretically be less expressive than autoregressive approaches, our experiments show no performance degradation across diverse tasks」。

#### 一个容易被忽略的代价：KV cache 没了

原版自回归时可以用 **KV cache**：把前面算过的注意力 key/value 缓存起来，第 2 次前向只算新增的那一个 token。所以第 2~7 个词其实比第 1 个快。

改成并行后，每次都是全长序列一次算完，cache 用不上。但**只算一次** ——总时间 0.0629 秒 vs 原来 0.2396 秒，快 **3.8 倍**。

用「每次都全算」换「只算一次」，这笔账很划算。但如果哪天 chunk 长度缩到 1（不要块），并行解码就没什么优势了——这也解释了为什么改动 3 和改动 5 必须一起做。

#### 代码里的一个坑（论文没写）

那排占位符后面还跟着**一个 stop token**：

```python
# Add (ACTION_DIM * NUM_ACTIONS_CHUNK) placeholder tokens to input_ids
placeholder_action_token_ids = torch.ones((bsz, ACTION_DIM * NUM_ACTIONS_CHUNK))
input_ids = torch.cat([input_ids, placeholder_action_token_ids], dim=-1)

# Add stop token to sequence (needed in non-causal bi-directional self-attention,
# as it appears at train time)
stop_token_id = torch.ones((bsz, 1)) * STOP_INDEX
input_ids = torch.cat([input_ids, stop_token_id], dim=-1)
```

注释写得很清楚：双向注意力下，训练时序列末尾有个 `</s>`，推理时不带上就**跟训练分布不一致**。这种「训练和推理必须严丝合缝」的细节，论文正文完全没提。

### 改动 4：离散 → 连续（图 2 给了真实数字）

#### 先看这组真实数字

图 2 右半把**同一组动作的两种存法**并排画出来了：

```
离散（robot action token #s）：  128  132   14  128  110  201  255
连续（raw robot action vector）：0.00 0.03 -0.82 0.00 -0.14 0.57 1.00
```

把编号代回桶中心公式（第 k 号桶中心 ≈ 2k/255 − 1），几乎一一对应：

| 编号 | 代回得到 | 连续值 |
|---|---|---|
| 128 | ≈ 0.00 | 0.00 |
| 132 | ≈ 0.04 | 0.03 |
| 110 | ≈ −0.14 | −0.14 |
| 201 | ≈ 0.58 | 0.57 |
| 255 | ≈ 1.00 | 1.00 |

**结论**：离散和连续不是两种模型，是**同一个动作的两种存法**——「第几号抽屉」vs「抽屉里的实际数值」。

#### 离散怎么编码的

1. 每个动作维度先归一化到 [-1, 1]。
2. 切成 **256 个桶**，记下每个桶的中心值 `bin_centers`。
3. 训练时：真值落在哪个桶，就把「那个桶对应的词」当标签，用交叉熵（next-token prediction）。
4. 推理时：模型输出词表上的分数分布，取 argmax → 桶编号 → 查 `bin_centers` → 数值。
5. 这些「动作词」占用 Llama 词表末尾的 256 个位置（`ACTION_TOKEN_BEGIN_IDX = 31743`，词表总 32000）。

#### 离散的两个毛病

**① 精度上限**：每格宽 2/256 ≈ **0.0078**。归一化后若对应 ±180°，就是 **±1.4°**——「捏拉链头」这种任务里够致命。

**② 桶边界抖动**：0.0039 和 0.0040 会被分到相邻两个桶。同一个动作，标签却在两个完全不同的「词」之间跳，训练信号变噪。

> 用个比喻：让你用一把刻度是 1 厘米的尺子量「头发丝粗细的偏差」。不是量不出来，是精度根本不够。

#### 改法

拆掉词表输出层（`lm_head` 到 32000 维的那一层不再用于动作），换一个 **4 层 MLP**（ReLU 激活）。

```
输入：该时间步的 D 个 token 的隐状态拼接 → (B, K, 14×4096 = 57344)
输出：(B, K, 14)，归一化到 [-1, 1]
```

代码里这个头叫 `L1RegressionActionHead`，内部是 `MLPResNet(num_blocks=2)`：

```
LayerNorm(57344) → Linear(57344→4096) → ReLU
→ [Block1: LayerNorm → Linear(4096→4096) → ReLU → 残差]
→ [Block2: 同上]
→ LayerNorm(4096) → Linear(4096→14)
```

正好 **4 个线性层**，对应论文说的「4 层 MLP」。

> **代码里才看得出的设计**：不是「一个 token 出一维动作」。代码先 `reshape(batch, NUM_ACTIONS_CHUNK, -1)`，把**同一时间步的 D 个 token 的隐状态拼成 57344 维**，再过 MLP，输出该步的 14 维。
> 也就是说：**一步内的 14 个关节是「一起商量」出来的**（左右手腕必须协调），而不是 14 个 token 各管各的。

#### 为什么 L1 而不是 L2

| 损失 | 最优解 | 后果 |
|---|---|---|
| L2 / MSE | **平均值** | 同一画面有两条都对的路径（左绕/右绕）时，平均成「直着撞过去」——一条不存在的路 |
| L1 | **中位数** | 被拉向其中一条真实路径，不凭空造；梯度恒定 ±1，小误差也学得动 |

举个具体例子：某个画面下有两条示教路径，动作第 1 维分别是 +0.6 和 −0.6。

- L2 学出来的是 **0**——中间那条谁也没走过的路。
- L1 学出来的是 **+0.6 或 −0.6**（中位数会落在其中一条上），至少是条真实路径。

另一个好处：L1 的梯度是常数（±1），误差再小也不会「学不动」；L2 的梯度跟误差成正比，接近收敛时越来越小，精度上不去。

#### 收益

表 I 里同一组配置（并行解码 + chunk）下比较：

| 配置 | LIBERO 平均成功率 |
|---|---|
| 离散 token + 交叉熵 | 90.2% |
| 连续 + 扩散 | 95.4% |
| **连续 + L1** | **95.3%** |

比离散高 **5 个点**，跟扩散打平，但推理只要一步（扩散要 10~50 步）。这就是改动 4 的价值：**用最便宜的损失拿到最贵方法的效果**。

### 改动 5：一次出 K 步（action chunking）

#### K 体现在哪

就体现在「占位符的数量」上：**K × D 个**。

| 平台 | K | D | 占位符数 | 换算成时间 |
|---|---|---|---|---|
| LIBERO（仿真） | 8 | 7 | 56 | 约 0.8 秒 |
| ALOHA（真机双臂） | 25 | 14 | 350 | **正好 1 秒**（25 Hz × 25 步） |
| Bridge（真机单臂） | 5 | 7 | 35 | — |

ALOHA 的 K=25 不是随手定的：控制频率 25 Hz，一次预测 25 步 = 覆盖 1 秒，是工程上的整数。

#### 为什么 K 大是好事

1. **摊薄成本**：出 1 步和出 25 步都是**一次前向**。吞吐从 15.9 Hz（K=1）涨到 **108.8 Hz**（K=8）。
2. **动作更连贯**：一次规划一段，段内是「一条想好的轨迹」，不会每 40 毫秒重新决策一次导致抖动。
3. **减少复合误差**：每一步都有小偏差，如果每步都重新决策，偏差会累积。一次看 25 步，模型可以「往前多看一点」来抵消当前的小偏差。

#### 为什么 K 大也是坏事

**块内不能改主意。** 一次算出 25 步，执行到第 3 步发现碗被碰歪了，得等第 25 步跑完才能重新规划——这期间机器人还在按「错误的计划」动。

论文图 6 给了个绝佳的反例：RDT-1B 在「舀料进碗」任务里，碗没放到位，它**继续往空处倒**——因为它一次预测 64 步，块内没有纠正机制，模型「以为自己还在碗上方」。而 π0 会重新尝试抓青椒，说明它对视觉反馈更敏感。

所以 K 是个权衡：**太小了算不过来，太大了反应迟钝**。这篇选 25（1 秒），并且在「执行整块」和「执行一半就重新规划」之间选了前者，理由是实测「既快又准」。

#### 代价的量化

加 K=8 让延迟从 0.0629 涨到 0.0735 秒（**+17%**），因为注意力序列变长了。但吞吐涨了 6.8 倍。

这个不对称是并行解码给的：**延迟几乎不变，吞吐线性增长**。

### 改动 6：FiLM——逼它真的读那句话（OFT 的「+」）

#### 问题长什么样

训练数据里，「舀葡萄干」和「舀椒盐卷饼」的画面**几乎一样**：同一个绿碗、同一把金属勺、同一个位置，只有食材堆里的东西不同。而指令只有几个单词的差别。

模型会走捷径：**不看指令，看画面猜**。训练集里葡萄干总在左边那一堆，它学到的是「往左边伸」，而不是「往葡萄干伸」。测试时换成椒盐卷饼（同样在左边），它仍然往左伸——碰巧对了。但如果换成「舀右边那堆」，它就错。

更麻烦的是，语言信息只在任务的**某一个瞬间**才关键：抓勺子的三个阶段（伸手、抓住、抬起来）跟指令无关，只有「往哪一堆去」那一下需要读指令。这让「学会看指令」变得很难——大部分时间读不读指令都没区别。

#### FiLM 的做法

看图 1 左半那些**绿色小块**：`task description (e.g., "scoop raisins into bowl")` 的箭头指向三个 ViT 块。这就是 FiLM，作用在**视觉编码器内部**，不是让语言在 LLM 里自己去竞争注意力。

数学上就一行：

```
F_new = (1 + γ) ⊙ F + β
```

- `F` 是视觉特征（每个 patch 的向量）
- `γ`（缩放）、`β`（平移）来自语言
- `⊙` 是逐元素相乘

#### 三个实现细节，每个都有坑

**坑 1：γ、β 作用在哪个维度上？**

这是最容易做错的地方。γ 和 β 是 **D_ViT 维**（比如 1152 维）的向量，作用方式是：

> 第 j 个元素，去缩放**全部 256 个 patch** 的第 j 维。

也就是**空间无关**的调制——同一层里所有 patch 用同一套 γ、β。

而不是「每个 patch 各有自己的 γ、β」（那样 γ 就得是 256×1152 的矩阵）。

论文明确说：按 patch 调制（后者）的语言跟随效果**明显更差**。原因是这个设计是从卷积网络的 FiLM 搬过来的——卷积里 γ、β 是 C 维（通道数），作用在整张特征图上，天然空间无关。

**坑 2：插在 transformer block 的哪里？**

代码里（`film_vit_wrapper.py`）的三行是整个 block 的全部内容：

```python
x = x + attn(norm1(x))          # ① 注意力 + 残差
x = x * (1 + γ) + β             # ② FiLM 插在这
x = x + mlp(norm2(x))           # ③ 前馈 + 残差
```

即**注意力之后、前馈之前**。为什么是这个位置？注意力负责「patch 之间交换信息」，前馈负责「每个 patch 各自加工」。在两者之间调制，等于「先让模型看清楚有什么，再用语言告诉它该重点看什么，最后各自加工」。

**坑 3：为什么是 1+γ 而不是 γ？**

初始化时 γ 和 β 接近 0。用 `1 + γ`，则初始化时 `F_new ≈ F`——**什么都没改**，预训练学到的视觉特征完好无损。如果直接用 `γ · F`，初始化时 γ≈0 会把特征全部清零，等于把视觉编码器废掉。

这个小技巧来自 FiLM 原论文，是「加一个模块但不破坏原有能力」的通用手法。

**最后一个细节：每层一套投影器。** 视觉编码器有 12 层，每层都有自己的 `scale` / `shift` 线性层。因为浅层看的是边缘和颜色，深层看的是物体和语义，需要不同的调制方式。

**γ、β 从哪来**：语言 token 的嵌入取**平均**（`average_language_embedding`），再各过一个线性层。用平均而不是逐个 token，是因为要的是「整句话的意思」，不是某个词。

#### 收益

论文图 5 的数字，两个依赖语言的任务（舀料、放锅）：

| 配置 | 语言跟随成功率 |
|---|---|
| OpenVLA-OFT（无 FiLM） | **33%** |
| OpenVLA-OFT+（有 FiLM） | **97%** |

33% 恰好是「随机三选一」的概率（三个目标物）。也就是说**去掉 FiLM 之后，模型完全没在读指令**。这是全篇最有说服力的一个消融。

**一个我看出来的隐患**：用整句嵌入的平均，词序信息丢了——「碗舀进葡萄干」和「葡萄干舀进碗」平均后一样。论文没有讨论这个。

### 2.3 为什么六处必须「一起改」（消融逻辑）

这是这篇论文方法论上最讲究的地方：它不是一个一个加模块堆分数，而是**每一处都有对照**。

| 配置 | LIBERO-Long | 平均 | 吞吐 | 说明 |
|---|---|---|---|---|
| 原版（自回归 + 离散） | 53.7 | 76.5 | 4.2 Hz | 基线 |
| + 并行解码（K=1） | — | — | 15.9 Hz | **只有速度**，没有性能数字 |
| + 并行解码 + chunk（K=8），仍离散 | 86.5 | 90.2 | 108.8 Hz | 速度 + 性能双涨 |
| + 连续 + 扩散 | 91.1 | 95.4 | 4.2 Hz（50 步） | 性能最高但慢 |
| **+ 连续 + L1** | 90.7 | **95.3** | **109.7 Hz** | 性能几乎一样，速度 26× |
| + 多相机 + 关节角 | **94.5** | **97.1** | 71.4 Hz | 再 +1.8 点 |

读这张表的三个要点：

1. **并行解码本身不贡献性能**（第一行 → 第二行，只有速度）。性能是 chunk 带来的（第二行 → 第三行）。
2. **连续动作贡献 5 点**，而 L1 与扩散性能几乎相同——所以选 L1 纯粹是为了速度。
3. **多相机 + 关节角贡献 1.8 点，但付出 35% 的吞吐**。这笔账只有在「速度已经有大量余量」时才划算——这又回到改动 3。

> 换句话说，改动 3 是**地基**：它先把速度拉到「有大量余量」的位置，后面三处改动（1、2、6）才有条件上线。

### 2.4 动作头到底有多大（我按层形状估的）

容易误以为「MLP 动作头很小」。按代码的形状算一下：

| 层 | 参数量 |
|---|---|
| `LayerNorm(57344)` | 114,688 |
| `Linear(57344 → 4096)` | 234,881,024 |
| Block1 `Linear(4096→4096)` | 16,781,312 |
| Block2 `Linear(4096→4096)` | 16,781,312 |
| `Linear(4096 → 14)` | 57,350 |
| **合计** | **≈ 2.68 亿** |

也就是说动作头有 **2.7 亿参数**——比 ACT 整个网络（8400 万）还大 3 倍，占 7B 基座的 3.6%。

这个数字有意思的地方在于：**它解释了为什么必须用 LoRA**。如果全参数微调，光这个新初始化的 2.7 亿参数就会把预训练权重带偏；用 LoRA 只训低秩增量，等于把「大改」限制在少数几个方向上。

### 2.5 三个常见误解

**误解 1：「并行解码 = 模型变笨了」**
不是。输出空间是固定长度的动作向量，不存在「该生成长度多少」的自由度；答案也不在输入里（占位符是空的）。实验上四个 suite 都没有退化。

**误解 2：「双向注意力会看到答案，等于作弊」**
训练时占位符是**空 embedding**，不是真值。真值只出现在 loss 计算里（`L1Loss(ground_truth, predicted)`），不进输入序列。所以不存在信息泄露。原版自回归训练时倒是真的会喂真值（teacher forcing）——那是为了防止「一步错步步错」，跟这里的并行不是一回事。

**误解 3：「连续动作不能表达多样做法」**
对，这是它的真实局限（论文 §8 自己承认）。L1 学的是中位数，遇到「同一画面有多种正确做法」时只会挑一种。但在这篇的实验设置里（每个任务只有一种做法），这个缺点不显现。

### 2.6 接口一览

| 平台 | 图像 | 状态 | K | D | 动作 token 数 | 序列总长（约） | 吞吐 | 延迟 |
|---|---|---|---|---|---|---|---|---|
| LIBERO | 1（可选 +腕部） | 8（可选） | 8 | 7 | 56 | 256~512 + 20 + 56 | 109.7 / 71.4 Hz | 0.073 / 0.112 s |
| ALOHA | 3 | 14 | 25 | 14 | 350 | 768 + 1 + 20 + 351 | 77.9 Hz | 0.321 s |

> ALOHA 那行的关键：**0.321 秒出 1 秒的动作**（25 步 ÷ 25 Hz）。能跑 25 Hz 不是因为算得比 40 ms 快，而是**算一次用一秒**——生成速度远大于消耗速度。

## ③ 训练

### 3.1 损失：L1 回归

```
L(θ) = (1/N) · Σ | a_pred − a_gt |,   a ∈ [-1, 1]^(K×D)
```

| 符号 | 是什么 | 形状 / 取值 |
|---|---|---|
| a_pred | 动作头 MLP 输出的归一化动作 | (K, D) = (25, 14) |
| a_gt | 示教数据的真实动作（同样归一化） | (25, 14) |
| N | 元素总数 | K×D = 350 |

代一组小数字（缩到 K=2、D=2 感受一下）：预测 `[[0.10, -0.20], [0.50, 0.00]]`，真值 `[[0.15, -0.10], [0.40, 0.30]]`，逐元素差 `[0.05, 0.10, 0.10, 0.30]`，平均 = **0.1375**。训练就是把 350 个这样的差值往下压。

论文的收敛判据就是这个数：**归一化 L1 损失降到 0.01 以下**（相当于平均每维偏差 1% 满量程）。

### 3.2 训练流程（没有多阶段，一次训完）

| 项 | LIBERO | ALOHA |
|---|---|---|
| 微调方式 | LoRA（r=32, α=16, dropout=0） | 同 |
| 步数 | 非扩散 50–150K / 扩散 100–250K | 50–150K |
| batch | 64–128 | 32 |
| 硬件 | 8× A100/H100 | 8× A100/H100-80GB |
| 学习率 | 5e-4 → 5e-5（100K 步后衰减） | 5e-4 → 5e-5（50K 步后衰减） |
| FiLM | 不用 | 用（OFT+） |
| 评测 | 每 50K 步存一次，报最好 | — |

> **为什么用 LoRA**：微调数据只有 500 条（LIBERO）到 300 条（ALOHA），相对预训练的 1M 条差三个数量级，全参数微调容易把预训练知识洗掉。LoRA 只在注意力/前馈的权重上加低秩旁路，r=32 意味着每个被适配的权重矩阵只学 32 维的增量。

### 3.3 训练和推理不一样的地方

| 环节 | 训练 | 推理 |
|---|---|---|
| 动作输入 | 空占位符（与推理一致） | 空占位符 |
| 步数 | 一次前向算完整个块，与真值比 | 同 |
| 去噪 | 无（L1 单步） | 无 |
| 输出 | 直接回归 | 直接回归 |

L1 版本训练和推理**完全对称**，这是它比扩散省事的地方——扩散训练时要随机采噪声和时间步、推理时要迭代去噪（50 步），两套流程。

1. 每张图缩到 224×224，归一化 → 复制成 6 通道（SigLIP 3 + DINOv2 3）。
2. 关节角与动作都用训练集的统计量归一化到 [-1,1]。
3. 动作块从当前时刻往后取 25 步（不足则截断/重复末尾）。
4. 多机器人维度不同怎么对齐：这篇不做跨本体统一——**每个平台一套常量**（`constants.py` 里按命令行参数自动选 LIBERO / ALOHA / BRIDGE）。

| 数据集 | 规模 | 机器人 | 采集方式 |

## ⑤ 输入输出信息流

### 5.1 一次前向（推理，ALOHA）

```
3 张 224×224×6 图 ──SigLIP+DINOv2（共享）──▶ 3 × 256 = 768 个 patch token
14 维关节角 ──2 层 MLP──▶ 1 个 token
指令 "scoop raisins into bowl" ──tokenizer──▶ ~20 个 token
                    ↓ 沿序列拼接（≈789 个位置）
        Llama-2 7B（双向注意力，一次前向）
                    ↓ 取动作位置那 350 个隐状态
       action head（MLPResNet）──▶ 25 × 14 的归一化动作
                    ↓ 反归一化（乘回训练集统计量）
            25 步绝对关节角目标 → 以 25 Hz 依次下发给控制器
```

**关键点**：

- **只算一次**，没有循环、没有去噪迭代、没有 KV cache。
- 350 个动作 token 是**输入里就准备好的空位**，不是生成出来的。
- 输出是**整块**，执行完 1 秒（25 步）后再拍新图、重新推理一次。

### 5.2 与原版的对比

| | 原版 OpenVLA | OpenVLA-OFT |
|---|---|---|
| 前向次数 | 7 次（每维一次） | 1 次（整块） |
| 输出 | 7 个离散编号 | 350 个实数（25×14） |
| 循环 | 有（逐 token） | 无 |
| 单次耗时 | 0.24 s / 步 | 0.32 s / 块 |

## ⑥ 例子走一遍（结构流程，非真实样本）

> 说明：这一节是按代码结构推的流程，**没有加载真实数据集验证数值**。标「代码确定」的是从代码读出来的，标「示意」的是为了讲清楚编的数。

场景：ALOHA，指令 `scoop raisins into bowl`。

**t = 0**

1. 拍三张图，取当前 14 维关节角 → 组成一条样本。（代码确定）
2. 三张图 → 768 个视觉 token；关节角 → 1 个 token；指令 → ~20 个 token。（代码确定）
3. 在序列末尾加 **350 个空占位符 + 1 个 stop token** = 序列总长约 1140。（代码确定）
4. 一次前向，取占位符那 350 个位置的隐状态。（代码确定）
5. 每 14 个 token 拼成一个 57344 维向量，过 MLP → 该步的 14 维动作。25 步 → (25, 14)。（代码确定）
6. 反归一化 → 25 步绝对关节角目标，标为 a_0 … a_24。（代码确定）

**t = 0 ~ 1 s（执行）**

7. 控制循环每 40 ms 取一步下发，25 步正好 1 秒。期间**不再推理**。（论文：执行完整块再重规划）

**t = 1 s**

8. 重新拍图、取关节角 → 回到第 1 步。上一块的缓存全部丢弃，不跨块复用。

**多轮之后**：稳定在「推理 0.32 s（后台）→ 执行 1 s」的节奏，只要推理时间 < 块时长，机器人就连续。

## ⑦ 实验与地位

### 7.1 LIBERO（仿真，表 I）

| 方法 | 平均成功率 |
|---|---|
| Diffusion Policy（从零训） | 72.4 |
| Octo（微调） | 75.1 |
| DiT Policy | 82.4 |
| **OpenVLA 原配方** | **76.5** |
| + 并行解码 & chunk（离散） | 90.2 |
| + 连续 & 扩散 | 95.4 |
| **+ 连续 & L1（= OpenVLA-OFT）** | **95.3** |
| π0（大规模双臂预训练 + flow matching） | 94.2 |
| **OpenVLA-OFT + 腕部图/状态** | **97.1** |

三组对照读出的三件事：① 并行 + chunk：**+14 点**（提速技巧同时提分）；② 连续 vs 离散：**+5 点**；③ L1 ≈ 扩散（95.3 vs 95.4），但推理 1 步 vs 50 步。

### 7.2 效率（表 II / 表 III）

| 配置 | 吞吐 | 延迟 | LIBERO-Long |
|---|---|---|---|
| OpenVLA | 4.2 Hz | 0.2396 s | 53.7% |
| + PD | 15.9 Hz | **0.0629 s** | — |
| + PD&AC | 108.8 Hz | 0.0735 s | 86.5% |
| + PD&AC, Cont-L1 | **109.7 Hz** | 0.0729 s | 90.7% |
| + Cont-扩散（50 步） | 4.2 Hz | 1.9070 s | 91.1% |
| + Cont-扩散（10 步） | 19.3 Hz | 0.4145 s | 91.0% |
| + Cont-扩散（1 步） | 109.4 Hz | 0.0731 s | **0.0%** |

最后一行值得记住：扩散降到 1 步，速度追上了 L1，但成功率归零——说明扩散的「多步」不是可省的额外开销，是它工作的前提。

**ALOHA 真机（表 III）**：

| 方法 | 参数量 | 吞吐 | 延迟 |
|---|---|---|---|
| OpenVLA | 7.5B | 1.8 Hz | 0.543 s |
| **OpenVLA-OFT+** | 7.5B | **77.9 Hz** | 0.321 s |
| RDT-1B | 1.2B | 84.1 Hz | 0.297 s |
| π0 | 3.3B | 291.6 Hz | 0.086 s |
| ACT | 84M | 432.8 Hz | 0.058 s |

小模型吞吐高很正常（ACT 只有 84M）。有意义的是 **OpenVLA-OFT+ 追平了比它小 7 倍的 RDT-1B**——因为它单次前向出整块，而扩散类要多步去噪。

### 7.3 消融

- **去掉预训练**：跳过 OpenVLA 预训练、直接用 OFT 配方微调底层 VLM → 平均成功率掉 **5.2 点**。说明预训练表示仍然有价值。
- **FiLM 换到 LIBERO**：几乎没影响（表 XIV）——因为 LIBERO 不加 FiLM 语言跟随已经不错。这解释了为什么只在 ALOHA 用 FiLM。
- **单一策略训四个 suite**：与分开训练效果相当（表 XIV）。

### 7.4 局限（作者承认的）

1. **多模态示教**：实验数据每个任务只有一种做法。L1 学中位数，遇到「同一画面多种正确做法」时可能只学一种；扩散能表达多模态但可能过拟合到次优模式。
2. **只验证了微调**：OFT 是否适用于预训练、大规模训练是否仍需扩散，未知。
3. **语言接地不一致**：无 FiLM 时 ALOHA 崩到 33%，但 LIBERO 加 FiLM 几乎没影响——原因不明。

### 7.5 这篇的地位

它是「VLA 微调」这条线上的基准配方：后续很多工作（包括各种开源 VLA 的微调脚本）默认就带 parallel decoding + action chunking + L1。它证明了「不换模型也能大幅改进」，同时也把「扩散/flow matching 是不是必须」这个问题摆到台面上——至少在数据量不大（几十到几百条示教）的微调场景，答案是不必须。

## 问答

- **Q（开讲前）**：这个 skill 是这样用的吗？
  **A**：是。一站一站讲，讲完停下问要不要继续；可以随时插话、跳站。
- **Q（② 站）**：OFT 相比 OpenVLA 具体改进了哪些方面？
  **A**：六处，前三处是主干——并行解码（双向注意力 + 空占位符）、连续动作 + L1、动作块 K。其余三处是补丁：多相机输入、proprio 关节角、FiLM 语言调制。六处互相咬合，不是六个独立小改进。
- **Q（② 站）**：离散动作和连续动作是什么关系？
  **A**：同一组动作的两种存法。离散是「第几号抽屉」（256 个桶的编号），连续是「抽屉里的实际数值」。图 2 给了同一动作的两行数字，可以互相验算。
- **Q（② 站）**：并行解码为什么不会让模型变笨？
  **A**：输出长度固定（K×D），答案不在输入里（占位符是空的），所以「一起填」没有损失；实验上四个 suite 无一退化。
- **Q（② 站）**：为什么六处必须一起改？
  **A**：并行解码只提速度不提分，分是 chunk 提的；而 chunk 和额外输入（多相机/关节角）的代价，只有并行解码拉出的吞吐余量才付得起。地基是 3，收益在 5，4 决定最后 5 个点。
